# S1: Foundation (no YouTube needed)

Goal: everything the recommend pipeline and UI stand on, buildable and testable without YouTube.

**Files owned (all under ``):** `src/schemas/*.ts` (new collection files), `src/schemas.ts`, `src/catalog.ts`, `src/contract.ts`, `src/recommend/filter.ts` (+ tests), `src/themes.css`, `src/themes.ts`, `index.html` (theme lines only).

**In scope (enumerated):**
1. Collections with per-user RBAC: `checkins`, `suggestions`, `savedVideos`, `preferences`, `usage`, `searchCache` (PLAN §4). Keep scaffold `users` + `settings`.
2. `src/catalog.ts`: types + 20 activities (meditation / movement / creative; goals calm, express, connect, move, break).
3. `src/contract.ts`: request/response types shared by worker and client.
4. `src/recommend/filter.ts`: pure deterministic hard filter (time, energy→effort cap, dislikes, avoid, exclusions, goal with relax).
5. "calm" theme from the palette in `CLAUDE.md`; make it the default.

**Out of scope:** the `recommend` action, LLM, YouTube, any screens, deploy.

**Acceptance (automated):** `npm run type-check`; `npm run test:unit` covering the filter and catalog integrity (unique ids, valid ranges, every goal has ≥2 activities, no forbidden words in user-facing strings).
**Acceptance (manual, Elena):** read the catalog titles/blurbs and confirm the tone; look at the theme in the running app later (S3).

**What these checks do NOT prove:** that RBAC actually isolates two real accounts (needs the two-account Playwright/manual test, scheduled with S2/S6); that catalog search queries return good videos (needs YouTube); that the `userBound` columns behave as documented when a client writes them.

**Risks / stop conditions:** if `userBound` or `uniqueOn` semantics differ from the docs, stop and revise. Never commit or deploy in this slice.

**Design decisions made here (Elena can change):**
- Every role including admin sees only its OWN check-ins, suggestions, saved videos, and preferences (nobody can read another person's notes). Changed 2026-10-01: an earlier version gave admin no access at all, which locked the app owner (pinned to admin) out of their own data.
- `usage` and `searchCache` are written only by server actions (members can't forge counters).
- Goal is a hard filter only if the user picked one; if fewer than two activities match, the filter relaxes the goal (never the hard constraints) and reports it.
